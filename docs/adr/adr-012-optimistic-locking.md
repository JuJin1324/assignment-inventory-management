# ADR-012: 동시성 제어 방식 — 낙관 락 선도입 후 데이터 기반 재검토

## 날짜

2026-06-03

## 상태

채택 (Accepted)

## 맥락

입고·출고가 모두 구현된 지금, 같은 상품에 대한 동시 요청이 발생하면 lost update(수량 덮어쓰기)·초과 출고가 생길 수 있다. 이를 막을 동시성 제어 방식을 결정해야 한다. DB는 PostgreSQL(MVCC)로 고정이다.

현시점에서 충돌이 얼마나 자주 발생하는지 측정된 데이터가 없다.

## 후보군

### 1. 낙관 락 (`@Version`)

JPA가 관리하는 버전 컬럼을 `Product`에 추가한다. 저장 시 버전을 비교해 불일치하면 `ObjectOptimisticLockingFailureException`을 던지고, 호출자가 재시도하거나 409로 응답한다.

- **장점:** 충돌이 드문 경우 블록 없이 진행 → 처리량이 높다. 구현이 단순하다(`@Version` 필드 추가). 충돌 발생 빈도를 예외 로그·메트릭으로 관측할 수 있다.
- **단점:** 충돌이 잦으면 재시도 비용이 누적된다. 재시도 로직을 호출자(서비스·핸들러)에서 처리해야 한다.

### 2. 비관 락 (`SELECT … FOR UPDATE`)

조회 시 행 락을 걸어 다른 트랜잭션이 같은 행을 읽지 못하게 블록한다.

- **장점:** 충돌이 잦은 경우 재시도 없이 순서 보장. 충돌 감지 후 처리 로직이 단순하다.
- **단점:** 충돌이 드문 경우에도 매 요청마다 블록이 걸려 처리량이 낮아진다. 데드락 위험이 있다.

## 결정

**낙관 락 (`@Version`)을 선도입한다.**

충돌 빈도 데이터가 없는 상태에서 비관 락을 바로 도입하면 충돌이 드문 경우에도 불필요한 블록 비용을 치른다. 낙관 락으로 먼저 운용하면서 충돌 예외 발생 빈도를 측정·관측한 뒤, 충돌이 잦다고 판단되면 비관 락으로 전환한다.

## 근거

충돌 빈도를 모르는 상태에서 비관 락을 선택하는 것은 아직 확인되지 않은 문제를 위해 처리량을 미리 희생하는 것이다. 낙관 락은 충돌이 드문 경우 최적이고, 충돌 예외를 통해 실제 빈도 데이터를 수집할 수 있어 다음 결정의 근거가 생긴다.

## 재검토 트리거

409 응답(충돌 재시도) 빈도가 유의미하게 높아지면 비관 락(`SELECT … FOR UPDATE`) 전환을 검토한다.
