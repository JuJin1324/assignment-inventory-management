# ADR-001: 레이어드 기반 + 헥사고날 요소 일부

## 날짜

2026-06-02

## 상태

채택 (Accepted)

## 맥락

재고 관리 MVP를 도메인-퍼스트로 짓는다 — 순수 도메인(in-memory)을 먼저 세우고, RDBMS 어댑터, 웹 어댑터를 차례로 붙인다. 도메인을 영속·웹에서 떼어내려는 선택들(도메인/JPA 엔티티 분리 검토, FP·ADT 도메인 모델링, in-memory→RDBMS 스왑)이 헥사고날을 가리킨다. 그러나 과제가 명시한 MVP 목적에 전면 포트·어댑터를 두는 풀 헥사고날은 과하다. 어떤 아키텍처로 갈지 정해야 한다.

## 후보군

### 1. 레이어드

Controller → Service → Repository → DB. 의존이 아래(DB)로 흐른다.

- **장점:** 단순·익숙하고 Spring 기본 흐름에 맞는다.
- **단점:** 도메인이 영속(JPA 엔티티)에 얹히기 쉽다. in-memory→RDBMS 스왑이 부자연스럽다.

### 2. 풀 헥사고날 (포트·어댑터 전면)

도메인이 중심, 모든 경계에 포트·어댑터.

- **장점:** 도메인 순수성이 가장 높다.
- **단점:** 포트·어댑터·매핑 보일러플레이트가 MVP 규모에 과하다.

### 3. 레이어드 기반 + 헥사고날 요소 일부

레이어드 용어·구조(controller/service/repository)를 유지하되, 핵심 경계(영속)에 의존 역전을 적용한다 — repository를 인터페이스로 두어 도메인이 JPA에 의존하지 않게 한다.

- **장점:** 익숙한 외피로 진입 비용이 낮으면서, 도메인 격리와 in-memory→JPA 스왑 가능성을 핵심 경계에서만 얻는다.
- **단점:** 순수 레이어드보다 약간의 추상화(인터페이스)가 는다.

## 결정

**레이어드 기반으로 가되, 헥사고날 요소를 일부 섞는다.** 레이어드 용어·구조로 표현하고, 영속 경계에 의존 역전(repository 인터페이스)을 적용해 도메인을 격리한다 — "레이어드 용어로 덮은 헥사고날."

## 근거

- 과제가 MVP 목적을 명시했고, 풀 헥사고날의 전면 포트·어댑터는 그 규모에 과하다.
- 그래도 도메인-퍼스트 빌드(in-memory → JPA 스왑)와 도메인 순수성(FP·ADT, 엔티티 분리)을 살리려면 영속 경계의 의존 역전은 필요하다.
- 레이어드의 익숙한 외피는 가독성·진입 비용을 낮추고, 헥사고날식 도메인 격리를 핵심 경계(영속)에만 한정해 보일러플레이트를 줄인다.
