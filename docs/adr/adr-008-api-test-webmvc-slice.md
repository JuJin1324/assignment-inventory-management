# ADR-008: API 계층 테스트 방식 — @WebMvcTest 컨트롤러 슬라이스

## 날짜

2026-06-02

## 상태

채택 (Accepted)

## 맥락

Story 4에서 출고 REST API(컨트롤러·요청/응답 DTO·에러 응답)를 더한다. 도메인(Story 1)·영속(Story 2)·서비스(Story 3)는 각자 테스트가 있다. 웹 계층의 새 관심사를 어떻게 테스트할지 정해야 한다.

## 후보군

### 1. 컨트롤러 슬라이스 (@WebMvcTest)

웹 계층만 띄우고 `ShipService`는 목으로 둔다.

- **장점:** 빠르다. 새 관심사(요청 매핑·입력 검증·상태 코드·JSON 직렬화·에러 응답)만 콕 집는다. 아래 계층은 이미 각자 테스트가 있어 중복이 없다.
- **단점:** 컨트롤러→서비스→도메인→DB 전 구간 연결은 보지 않는다.

### 2. 통합테스트 (@SpringBootTest + MockMvc)

전체 컨텍스트를 띄워 end-to-end로 본다.

- **장점:** 전 구간 연결까지 한 번에.
- **단점:** 느리고, 이미 테스트된 아래 계층을 다시 덮는다.

## 결정

**@WebMvcTest 컨트롤러 슬라이스로 간다.** `ShipService`를 목으로 두고 웹 계층만 검증한다.

## 근거

- 계층마다 표적 테스트를 둔 흐름(도메인 단위 → 영속 `@DataJpaTest` → 서비스 목 단위)과 한 결이다. 웹의 새 관심사(검증·상태 코드·에러 매핑)를 슬라이스로 빠르게 잡는다.
- 컨트롤러→서비스→도메인→DB 전 구간 연결은 Story 4 완료 기준의 "앱 띄워 실제 HTTP 요청으로 확인"(수동)으로 덮는다.

## 재검토 트리거

전 구간 연결을 자동으로 회귀 검증할 필요가 커지면(예: 회귀가 잦은 통합 지점이 생기면) 통합테스트를 추가한다.
