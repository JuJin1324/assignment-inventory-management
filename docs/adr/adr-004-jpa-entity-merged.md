# ADR-004: 도메인=JPA 엔티티 통합 + 공통 컬럼 규약

## 상태

채택 (Accepted)

## 맥락

Story 2에서 순수 도메인(`Stock`)을 PostgreSQL에 영속한다. 영속은 JPA로 확정했고, 도메인 엔티티와 JPA 엔티티를 분리할지 하나로 둘지 정해야 한다. ADR-001은 영속 경계에 의존 역전을 적용해 도메인을 격리하려 했다.

## 후보군

### 1. 분리

도메인 `Stock`은 순수 유지, 별도 `@Entity` JPA 클래스 + 도메인↔엔티티 매핑.

- **장점:** 도메인이 JPA 어노테이션·no-arg 생성자·식별자 전략에 묶이지 않는다. ADR-001(헥사고날 요소·의존 역전)과 정합. Story 1 도메인 코드를 안 건드린다.
- **단점:** 매핑 코드·필드 중복(보일러플레이트), 변환 계층이 는다.

### 2. 하나로

도메인 `Stock`에 직접 `@Entity`·`@Id`를 매핑.

- **장점:** 매핑·변환 코드 없음, 단순. 대부분의 Spring 프로젝트 관행.
- **단점:** 도메인이 JPA에 묶인다(no-arg 생성자 강제, 어노테이션 침투, 영속 관심사 누수).

## 결정

**하나로 간다.** 도메인 `Stock`에 직접 JPA를 매핑한다. 더불어:

- **공통 컬럼 규약** — 모든 영속 엔티티는 `createdAt`·`updatedAt`·`version`을 갖는다. `BaseEntity`(`@MappedSuperclass` + JPA Auditing)로 묶어 상속시켜 엔티티마다 반복하지 않는다.
- **낙관적 락** — `@Version`으로 둔다.

## 근거

- **MVP 단순성 우선** — 매핑·변환 보일러플레이트를 없애고, 익숙한 Spring 관행으로 진입 비용을 낮춘다.
- **인정하는 트레이드오프** — 하나로 가면 도메인이 JPA 어노테이션·no-arg 생성자를 갖게 되어, ADR-001이 지향한 도메인 격리 의도의 일부를 내려놓는다. 단위 테스트(동작)는 그대로 통과하므로 도메인 *로직*은 보존된다. 격리가 다시 필요해지면 재검토 트리거로 분리를 다시 본다.
- **공통 컬럼을 BaseEntity로** — 감사 컬럼·낙관락을 한 곳에 모아 엔티티 전반에 일관되게 적용하고 반복을 없앤다.

### 낙관적 락의 경계

`@Version` 컬럼 + JPA 기본 강제까지가 이 결정의 범위다 — 동시 충돌 시 `OptimisticLockException`이 발생한다. 그러나 **충돌을 어떻게 처리할지**(재시도, 사용자에게 돌려줄 에러 응답, 동시성 시나리오 테스트)는 별도 **"동시 재고 변경 충돌" 에픽** 몫이다. Story 2는 컬럼과 기본 강제까지만 세우고 충돌 처리 로직·동시성 테스트는 만들지 않는다.

## 재검토 트리거

도메인이 영속에서 다시 떼어내야 할 만큼 복잡해지거나, JPA 어노테이션·영속 관심사가 도메인 로직을 방해하면 분리(별도 엔티티 + 매핑)를 다시 본다.
