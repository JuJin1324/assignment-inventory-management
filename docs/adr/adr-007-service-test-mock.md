# ADR-007: 서비스 테스트 방식 — repository 목 단위테스트

## 상태

채택 (Accepted)

## 맥락

Story 3에서 출고 서비스를 세운다 — 재고 조회 → 도메인 `ship` → 저장으로 출고를 오케스트레이션한다. 도메인(Story 1)·영속(Story 2)은 각자 테스트가 있다. 서비스의 새 관심사(조정 로직)를 어떻게 테스트할지 정해야 한다.

## 후보군

### 1. repository 목 단위테스트

`StockRepository`를 Mockito로 목 처리하고 서비스 로직만 격리해 검증.

- **장점:** 빠르다(스프링·DB 안 띄움). 서비스의 새 관심사인 조정 로직(부족 시 저장 안 함, 성공 시 차감·저장)만 콕 집는다. 도메인·영속은 이미 각자 테스트가 있어 중복이 없다.
- **단점:** 트랜잭션 경계·실제 저장은 목이라 타지 않는다.

### 2. 영속까지 묶은 통합

실제 서비스 + 실제 repository(H2)로 전 구간을 검증.

- **장점:** 서비스+영속 연결·실제 저장까지 본다.
- **단점:** 느리고, Story 2의 영속 테스트와 겹친다.

## 결정

**repository를 목으로 둔 단위테스트로 간다.** 서비스 조정 로직을 격리해 검증한다.

## 근거

- 계층마다 표적 테스트를 둔 흐름(도메인 단위 → 영속 `@DataJpaTest`)과 한 결이다. 서비스의 새 관심사는 *조정*이고, 목으로 그 조정(성공 시 차감·저장 호출, 부족 시 저장 호출 안 함)을 빠르게 잡는다.
- 트랜잭션 경계는 `@Transactional`을 거는 것으로 두고, 실제 저장·전 구간 연결은 Story 4의 수동 e2e와 Story 2의 영속 테스트가 덮는다.

## 재검토 트리거

서비스 조정이 복잡해지거나(여러 repository·외부 호출), 트랜잭션·동시성 정확성이 실제 위험이 되면 통합테스트로 올린다.
