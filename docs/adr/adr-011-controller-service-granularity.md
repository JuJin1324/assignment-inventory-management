# ADR-011: 컨트롤러·서비스 입자 규약 — 리소스 묶기 / 유스케이스 분리

## 날짜

2026-06-03

## 상태

채택 (Accepted)

## 맥락

출고 에픽에서 기능이 `ship` 하나뿐일 때는 컨트롤러·서비스를 어떻게 나눌지 추측 설계를 피해 결정을 보류했다(백로그 결정 메모). 입고 에픽(Story 2)에서 `receive`가 합류해 두 번째 유스케이스가 생긴 지금이 그 트리거다 — 구체 케이스 둘을 놓고 결정한다.

## 후보군

### 컨트롤러: 액션별 분리 vs 리소스 묶기

**액션별 분리** — `ShipmentController`, `ReceiveController`처럼 유스케이스마다 컨트롤러를 둔다.

- **장점:** 컨트롤러 파일이 작다.
- **단점:** 상품이라는 리소스가 파일에 흩어진다. 엔드포인트 경로 체계(`/api/products/*`)를 한 곳에서 볼 수 없다. 기능이 늘수록 컨트롤러 파일이 늘어나 경로 전체를 파악하기 어렵다.

**리소스 묶기** — `ProductController` 하나가 `/api/products/*` 전체를 담당한다.

- **장점:** 상품 리소스의 엔드포인트 전체가 한 파일에 모인다. 경로 체계를 한눈에 파악할 수 있다.
- **단점:** 유스케이스가 많아지면 컨트롤러 파일이 길어진다.

### 서비스: 도메인 단위 묶기 vs 유스케이스별 분리

**도메인 단위 묶기** — `ProductService` 하나가 출고·입고·조회 등을 모두 담당한다.

- **장점:** 파일 수가 적다.
- **단점:** 기능이 늘수록 god-service로 비대해진다. 유스케이스 간 의존이 섞여 테스트 범위가 불명확해진다.

**유스케이스별 분리** — `ShipService`, `ReceiveService`처럼 유스케이스마다 서비스를 둔다.

- **장점:** 각 서비스의 책임이 명확하다. 목 범위가 작아 테스트가 간결하다.
- **단점:** 파일 수가 늘어난다.

## 결정

- **컨트롤러는 리소스 단위로 묶는다.** `ProductController` 하나가 `/api/products/*`를 담당한다.
- **서비스는 유스케이스 단위로 분리한다.** `ShipService`·`ReceiveService`처럼 유스케이스마다 서비스를 둔다.

## 근거

컨트롤러는 *경로 체계*를 소유한다. 리소스로 묶으면 어떤 엔드포인트가 있는지 한 파일에서 파악되고, 경로 일관성을 유지하기 쉽다. 서비스는 *오케스트레이션 단위*다. 유스케이스별로 분리하면 책임이 명확하고 테스트 목 범위가 작아진다. 두 결정은 역방향 — 컨트롤러는 묶고, 서비스는 쪼갠다 — 이어서 한 쌍으로 운용한다.

## 테스트 규약

컨트롤러가 하나로 묶이면 테스트 파일도 하나로 따라가면 기능이 늘수록 길어진다. 테스트는 **기능(유스케이스) 단위로 파일을 분리**한다.

- `ProductShipControllerTest` — 출고 엔드포인트 슬라이스 테스트
- `ProductReceiveControllerTest` — 입고 엔드포인트 슬라이스 테스트

프로덕션 코드는 리소스로 묶고, 테스트는 유스케이스로 쪼갠다. 컨트롤러가 길어지는 문제를 테스트 분리로 상쇄하고, 각 테스트 파일의 목(mock) 범위도 해당 유스케이스 서비스 하나로 좁아진다.

## 재검토 트리거

유스케이스가 많아져 `ProductController`가 지나치게 길어지면 서브 리소스 분리를 검토한다.
