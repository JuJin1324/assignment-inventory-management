# Story 5 — 모델링 동기화 (실행 기록)

입력: [../stories.md](../stories.md) §Story 5

## 무엇을 했는가

출고 구현(Story 1~4)의 계층 구조를 별도 구조 문서로 모델링에 더했다 — [docs/modeling/structure-ship.md](../../../../modeling/structure-ship.md). 컨트롤러 → 서비스 → 도메인(재고) → 리포지토리의 레이어드 구조를 *다이어그램 → 설명 → 각 컴포넌트* 3단으로 그렸다.

계획은 기존 *출고 시나리오*(`scenarios.md`)를 계층 통신으로 다시 그리는 것이었으나, 실행 중 방향을 틀었다 — 시나리오는 추상 수준(시스템·저장소)으로 되돌리고, 계층 구조는 새 구조 문서로 분리했다.

## 근거·결정 사항

- **계층 통신은 시나리오가 아니라 구조 문서로** — 출고 시나리오에 네 결과(200·409·404·400)를 계층별 분기로 다 담으니 중첩 alt가 세 겹이 돼 지저분했다. 시나리오는 *이해관계자 흐름*을 보는 자리라 추상 수준(시스템·저장소)을 유지하고, *계층이 어떻게 섰나*는 구조 문서가 맡는 게 각 문서의 역할에 맞다. 그래서 `scenarios.md` 출고 처리는 원래대로 되돌렸다.
- **`structure.md`와 분리** — `structure.md`는 *무엇이 있나*(도메인 개념 — 상품·재고·변동 이력), `structure-ship.md`는 *출고가 실제로 어떤 계층으로 섰나*. 도메인 개념 모델과 구현 계층 구조를 한 문서에 섞지 않는다.
- **파일명 `structure-ship.md`** — 출고(ship) 구현 구조임을 이름으로 드러낸다.
- **다이어그램 범위** — 재고 담당자(진입)·PostgreSQL(영속 대상)을 양 끝에 두고 컨트롤러~리포지토리를 채웠다. 서비스에서 갈라지는 두 화살표(도메인엔 "출고 검증·차감 위임", 리포지토리엔 "재고 조회·저장")로 판단과 영속의 분업을 드러낸다.

## 결과

- 신규: `docs/modeling/structure-ship.md`
- 되돌림: `docs/modeling/scenarios.md` 출고 처리(계층 재작도 시도 후 원복)

## 완료 기준 점검

실행 중 방향을 틀어(시나리오 재작도 → 별도 구조 문서 신설), Story 5 정의의 완료 기준도 실행에 맞춰 갱신했다([../stories.md](../stories.md) §Story 5). 갱신된 기준 대비:

- [x] 출고 구현의 계층 구조(컨트롤러 → 서비스 → 도메인 → 리포지토리)가 별도 구조 문서로 모델링에 더해진다
- [x] 그 문서가 도메인 개념 구조(`structure.md`)와 분리된다
- [x] 시나리오는 이해관계자 흐름의 추상 수준을 유지한다
- [x] 시스템 전체 비전(입고·조회·이력, Product·Movement)은 그대로 둔다
